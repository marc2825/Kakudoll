# エディタ UI の見直し（2026-11-23）

Kakudoll Editor の画面を見直したときの記録です。
現状の問題点、作り直しの 3 案、選んだ案と、実装した内容をまとめています。

操作できるモックアップ付きの版は [editor-ui-proposals-2026-11-23.html](../assets/design/editor-ui-proposals-2026-11-23.html) です（ブラウザで開きます）。

## 調べ方

UXML・USS・C# のコードを読んで診断しました。Unity を起動して画面を確かめてはいません。
面積の割合は USS に書かれた寸法から計算した概算です。各指摘には、根拠になったファイルと行を添えています（行番号は 2026-11-23 時点の `3a1e0f9`）。

## 要点

- **主役が小さい。** 最小サイズ（900×760）では、編集ビューはウィンドウ面積の約 5% です。1920×1000 でも約 22% でした。
- **同じことを何度も聞く。** 「どのメッシュを直すか」を 3 か所で別々に指定します。食い違うとエラーになります。
- **読む場所が決まっていない。** 操作の結果や次の手順が、画面の 9 か所に分かれて表示されます。
- ティザー画像は Kakudoll を「角度の軸にキーが並ぶ」絵で説明していますが、エディタにはこの軸がどこにもありません。

### 最小サイズでの面積の内訳

| 領域 | 割合 |
|---|---:|
| 編集ビュー | 約 5% |
| 比較ビュー 2 つ | 約 4% |
| 操作パネル（視点、表情、頂点選択） | 約 12% |
| 左ペイン（ドキュメント、キー一覧、旧形式） | 約 20% |
| 右ペイン（選択キー、対象 Mesh、BlendShape 取込、グループ設定） | 約 28% |
| 検証結果（問題がなくても常に表示） | 約 15% |
| バー類と余白 | 約 16% |

## 診断

指摘は 34 件です。重さは次の 3 段階にしました。

- 高: 作業が止まる、誤操作につながる
- 中: 毎回の手間になる
- 低: 仕上げの問題

### 今の画面で良い点（残すもの）

- 元の VRM を書き換えないことを、画面の言葉でも繰り返し伝えている
- 手順ガイドが状態を見て次の一手を示す、という考え方
- 1 回のドラッグを 1 回の「元に戻す」で戻せる。Unity が落ちても復元できる
- 色は Unity のテーマ変数が基本で、ライトとダークの両方で読める
- ほぼすべての操作にツールチップがある
- 検証結果は重複をまとめ、クリックで該当箇所に飛べる
- 性能やリソースの情報は折りたたんである

## 作り直しの前提

参考にした frontend-design スキルは「題材の世界から形を決める」「大胆さは 1 か所に使い、ほかは静かに」「言葉は利用者の側から書く」「動きは操作への反応に限る」を求めています。

Unity 2022.3 の UI Toolkit には、標準ではグラデーションも影もぼかしもありません。日本語フォントの同梱も容量とライセンスの負担が大きくなります。
そこで個性は書体や飾りではなく、構造と 1 つの専用部品（角度の軸）で出し、まわりは Unity 標準の見た目のまま静かにします。
色は 1 つだけ足します。オレンジは「キー」と「効く範囲」だけに使い、Unity の青は選択とフォーカスのために残します。

### 言葉の統一

| 今の画面 | 新しい言葉 |
|---|---|
| Yaw | 角度（必要な所だけ「左右の向き」） |
| Yawキー、Keyform、形状キー | キー |
| 対象Mesh、Binding、Renderer、Source Mesh | 直すパーツ |
| 位置差分、Vertex deltas | 形（「312 頂点を動かしています」） |
| 支持区間 開始・終了 | 効く範囲 |
| 補正を表示、After | 補正を表示（Space を押すあいだは補正前） |
| 頂点選択、Geometry Selection | 選ぶ |
| 2Dドラッグ、Keyform 2D編集 | 動かす |
| Main、Sub A、Sub B | 編集ビュー、比較 A、比較 B |
| ソフト半径、減衰 | なじませる範囲、なじませ方 |

## 決めたこと

**案A を骨組みにし、案C の「はじめる画面」を入口に使う**（2026-11-23、所有者が承認）。

- 角度の軸は、A1・A4・A5・B4・D2 を 1 つの部品でまとめて解決できる。ブランドの絵と画面がつながるのもこの案だけ。
- 入口に案C の「はじめる画面」を使い、最初のつまずき（A2、A6、B5）を先に取り除く。
- 案B の横並びは、あとから「見比べ表示」として足せる。
- UI の要素名の契約（K-025）は改訂する（[DECISIONS](DECISIONS.md) の K-037）。

## 実装したこと（2026-11-24）

| 場所 | 内容 | 主に解決する指摘 |
|---|---|---|
| はじめる画面 | グループのない新しいファイルで出す。アバター、直すパーツ（プレビュー用 VRM の SkinnedMeshRenderer の一覧）、角度（0° は必ず作る）を選び、「編集をはじめる」でグループ作成・パーツ指定・キー作成を 1 回の「元に戻す」にまとめて行う。終わると 45° のキーを選び、「選ぶ」ツールにする | A2、A6、B5 |
| 角度レール | 編集ビューの下の専用部品（`VlatAngleRail`）。キー（塗りつぶしは形を変えたキー）、効く範囲の帯、編集ビューの角度（白い印）、比較ビューの角度（A・B）を描く。ひし形を押すとそのキーを選んで編集ビューをその角度へ、横に引くとキーの角度を変える。何もない所を引くと編集ビューが回り、A・B を引くと比較ビューが回る | A1、A4、A5、B4、D2 |
| キーを足す | 今見ている角度に足す。その角度にキーがあるか効く範囲の外なら、いちばん広く空いている角度に足し、ボタンの文字にその角度を出す | D2 |
| ツール | 左の列に「見る・選ぶ・動かす」。1 つだけが選ばれ、使えないときはツールチップに理由を出す | A3、D3 |
| キーボード | 1・2・3 でツール、← → でとなりのキー、Space を押すあいだは補正前、[ ] でブラシの太さ。文字を入力している欄では横取りしない | D1、D4 |
| 編集ビュー | 1 つのビューを大きく取り、比較ビュー 2 つを右上に小さく重ねる（狭いときはさらに小さくし、もっと狭いと隠す）。左上に何の形を見ているか（「45° と 90° のあいだの形」など）を出す。ドラッグ中は比較ビューの見出しに「手を離すと更新」と出す | B1、A5、D6 |
| 右の列 | いまのツールの設定だけを出す。その下に選んでいるキー（角度、形の状態、この角度で見る、BlendShape の取り込み）と直すパーツ、いちばん下にアバター | B4 |
| 詳細 | 検証結果、効く範囲とグループ、シーンのアバターでのパーツ指定、ファイルの情報、プレビューの詳細を右端にまとめる。上のバーの「詳細」か検証結果の印で開く | B3、C2 |
| ステータス行 | 左に次にすること（今の状態から 1 文）、右に最後に起きたこと（操作の結果）を出す。手順の「済み」は持たない | B2、F1、F2 |
| 言葉 | 上の「言葉の統一」に合わせた。操作の結果を操作ごとの文にし（「45° にキーを足しました。」など）、ドラッグや保存のエラーには直し方を書いた | C1、C3、C4、C5 |
| 見た目 | 足す色はオレンジ 1 色（キーと効く範囲）。文字は 11px 以上、不透明度で薄くしない。最小サイズは 760×560、初めて開くときは 1180×760 | E1、E2、B6、B7 |
| 旧形式 | v0.1 の Layer 編集は、旧形式のファイルのときと「旧形式（v0.1）で始める」を選んだときだけ右の列に出す | A7 |

確認したこと:

- Unity 2022.3.62f3（Windows 11、WSL から実行）の EditMode テスト 415 件がすべて合格（変更前は 413 件。新しい画面のテストを 2 件足した）。PlayMode 4 件も合格。
- Unity 不要のテスト（`scripts/run_license_free_checks.py`）は合格。配布していないファイルが要る 5 件は NOT RUN。
- 実際のウィンドウのスクリーンショット（`VlatEditor1EProbe.UiSnapshot`、900×754、合成アバター）で、はじめる画面・キー選択・頂点選択・動かす・詳細を開いた状態を目で確かめた。
  batchmode ではライトテーマになり、撮った画像は色が実際より暗く写る。ダークテーマと、人が実際に操作したときの使い心地は確かめていない。

まだやっていないこと:

- キーごとの小さな絵をレールの上に並べる（案A のモックアップにあったもの）。キーの数だけ描く仕組みが要る。
- 案B の「見比べ表示」（キーを横に並べて大きく見る）。
- 「動かす」でドラッグする前に、選んだ頂点の印を出すこと（今は表示がキーの形になり位置がずれるため出していない）。
