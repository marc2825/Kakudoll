Kakudoll エディタ UI 改訂案

現在のエディタ画面を、コード（UXML・USS・C#）から読み取れる事実にもとづいて診断し、作り直しの方向を3案にまとめました。実装はまだしていません。案はどれも下のモックアップで実際に触れます。

正面 0°ななめ 45°横 90°

ティザー画像は Kakudoll を「角度の軸にキーが並ぶ」絵で説明しています。ところが今のエディタには、この軸がどこにも描かれていません。診断でいちばん大きかったのはこの点です。

要点

主役が小さい

最小サイズ（900×760）では、編集ビューはウィンドウ面積の約5%です。フルHDでも約2割にとどまります。

同じことを何度も聞く

「どのメッシュを直すか」を3か所で別々に指定します。食い違うとエラーになります。

読む場所が決まっていない

操作の結果や次の手順が、画面の9か所に分かれて表示されます。

現状の診断

指摘は全部で34件あります。重さは、作業が止まる・誤操作につながるものを「高」、毎回の手間になるものを「中」、仕上げの問題を「低」としました。根拠として該当するファイルと行を添えています。診断はコードを読んで行いました。Unity を起動して画面を確かめてはいないので、実際の見え方と違う所があれば教えてください。

A. 考え方と画面のずれ

A1高
角度の軸が画面にない

キーは「45°　120 頂点」という文字の一覧と数値欄だけで表されます。今の視点がどのキーのあいだにあるか、補間がどう効いているか、効く範囲がどこまでかを図で確かめられません。VlatEditorWindow.uxml:49 VlatEditorWindow.Keyforms.cs:40, 200-203

A2高
直すメッシュを3か所で指定する

「VRMを開く」（プレビュー用の複製）、右ペインの Avatar Root と Renderer の欄（シーン上のオブジェクト）、頂点選択の「対象」の3つです。プレビュー用の VRM は非表示のプレビューシーンに置かれるので、右ペインの欄を埋めるには同じアバターを別にシーンへ置くことになります。3つが食い違うと「選択RendererがKeyformのMeshBindingと異なります」と出て編集できません。Keyforms.cs:149-176 VlatPreviewController.cs:95 VlatPreviewController.Drag.cs:61

A3高
編集の段階が2つのチェックボックスで表される

実際は「見る、選ぶ、動かす」の3段階ですが、画面では「頂点選択」「2Dドラッグ」という独立したチェックに見えます。左ドラッグの意味は段階によって回転・選択・変形と変わります。ドラッグに入ると選んだ頂点の表示が消えます。頂点選択に入ると表情と補正表示が無効になりますが、理由は表示されません。uxml:90-91 VlatEditorWindow.cs:1592-1598, 1614

A4中
キーを選んでも視点が変わらない

45°のキーを選んでも視点はそのままで、右ペインの「視点をこのキー角度へ」を押す必要があります。一方ドラッグ中は「Mainは選択キー固定」になり、見えている形が補間結果なのかキーそのものなのかが状態によって入れ替わります。Keyforms.cs:111-130 VlatPreviewController.cs:1196

A5中
比較ビューの見出しが固定の文字

「Sub A (45°)」は UXML に直接書かれた文字で、ビューを回しても変わりません。比較ビューはキーとも連動しません。uxml:108, 115

A6中
1つしか作れないグループに一覧がある

グループは1つだけの対応ですが、一覧と追加・削除ボタンがあり、手順にも「2 グループ」があります。利用者が判断することのない作業です。VlatEditorKeyformController.cs:16 uxml:38-43

A7低
旧形式の区画が常に見えている

v0.1 の Layer 編集が左ペインに常駐します。見出しには「(v0.2)」「(v0.1互換)」という内部の形式番号が出ています。uxml:37, 52

今の画面で良い点（残すもの）

  • 元の VRM を書き換えないことを、画面の言葉でも繰り返し伝えている
  • 手順ガイドが状態を見て次の一手を示す、という考え方
  • 1回のドラッグを1回の「元に戻す」で戻せる。Unity が落ちても復元できる
  • 色は Unity のテーマ変数が基本で、ライトとダークの両方で読める
  • ほぼすべての操作にツールチップがある
  • 検証結果は重複をまとめ、クリックで該当箇所に飛べる
  • 性能やリソースの情報は折りたたんである
  • 段階に応じて操作ヘルプの文が変わる

作り直しの前提

frontend-design の考え方を Unity に当てはめる

参考にしたスキルは「題材の世界から形を決める」「大胆さは1か所に使い、ほかは静かに」「言葉は利用者の側から書く」「動きは操作への反応に限る」を求めています。

Unity 2022.3 の UI Toolkit には、標準ではグラデーションも影もぼかしもありません。日本語フォントを同梱するのも容量とライセンスの負担が大きくなります。そこで個性は書体や飾りではなく、構造と、1つの専用部品で出します。その部品が「角度の軸」です。まわりは Unity 標準の見た目のまま静かにします。

色は1つだけ足します。オレンジは「キー」と「今の角度」だけに使い、Unity の青は選択とフォーカスのために残します。

どの案でも行う改善

  • VRM を開いたら、直すパーツを一覧から選ぶだけにする。Avatar Root と Renderer の欄はなくす（A2, A6）
  • 編集の段階を「見る・選ぶ・動かす」の3つのツールにし、1・2・3 キーで切り替える（A3, D1）
  • メッセージは1か所にまとめる。検証結果は問題があるときだけ開く（B2, B3）
  • 押せないボタンには、ツールチップで理由を出す（D3）
  • 旧形式の区画は、旧形式のファイルを開いたときだけ出す（A7）
  • 実装の注記は「詳細」に移す。エラーには対処を書く（C2, C3）
  • 文字は11px以上、不透明度で薄くしない。コントラストは4.5:1以上（E1）

3つの案

3案は見た目の違いではなく、画面を何で組み立てるかが違います。A は角度の軸、B は横並びの見比べ、C は手順の少なさを中心に置いています。

案A 角度レール：角度の軸を画面の中心にする

ビューの下に角度の軸を置きます。キー一覧、Yaw スライダー、「視点をこのキー角度へ」、比較ビューの4つを、この1つの部品にまとめます。動画編集のタイムラインと同じ考え方で、時間の代わりに角度が流れます。

試す：レールをドラッグすると顔が回ります。ひし形を押すとそのキーに移動します。キーのない角度で「この角度にキーを足す」を押せます。

front_hair.vlat.json未保存 問題なし
正面 0° と比較
オレンジの帯が、補正の効く範囲

変わること

  • キーを選ぶと視点もその角度に合う。合わせるボタンは不要になる（A4）
  • キーのあいだを動かすと補間の途中の形がそのまま見える（A1）
  • キーは今見ている角度に足せる。ひし形を横に引けば角度を変えられる（D2）
  • 各キーの小さな絵がひし形の上に並ぶ。全部のキーの形を一度に見渡せる
  • ビューは1つで大きい。比べたい角度だけ右上に留める（B1, A5）
  • ツールの設定は右の細い列に、選んでいるツールの分だけ出る（B4）

長所と短所

  • 長所：ティザーの絵と画面が同じ形になる。説明なしで仕組みが伝わる
  • 長所：キーが16個に増えても破綻しない
  • 短所：レールは専用部品として新しく作る（Painter2D で描画）。3案でいちばん実装が重い
  • 短所：キーごとの小さな絵を描く負荷が増える。確定したときだけ更新する設計が必要
  • 短所：大きく並べて見比べる用途は案Bに劣る
  • 影響：UXML の要素名が大きく変わる。K-025 の改訂と UI テストの書き直しが必要

案B 見比べシート：キーを横に並べる

アニメの設定画（正面・ななめ・横を並べた絵）と同じ形にします。キー1つが1列で、押した列が編集ビューになります。横に通る補助線で、目やあごの高さが角度ごとにそろっているかを確かめられます。

試す：列を押すと、その角度が編集ビューになります。右端のスライダーでキーのあいだの形を確かめられます。

front_hair.vlat.json未保存 問題なし

変わること

  • キー一覧がなくなる。列がそのままキーになる（A1, A4）
  • 列のあいだの「＋」で、そのあいだにキーを足す（D2）
  • ツールは編集中の列の中に浮かぶ。ポインタの移動が短い（B4）
  • 編集していない列は、確定のたびに更新する。古い表示のあいだは見出しに印を出す（D6）
  • 「あいだ」の列で、補間の途中の形を確かめる

長所と短所

  • 長所：角度どうしの見比べがいちばんしやすい。Kakudoll の目的に直結する
  • 長所：今ある3ビューの仕組み（Main と Sub A・B）を流用できる。実装は中くらい
  • 短所：1つのビューは案Aより小さい
  • 短所：キーが4つを超えると横スクロールになる
  • 短所：今は Main だけが編集できる作りなので、列を切り替えるたびに Main を割り当て直す処理が要る
  • 影響：プレビューの要素名は残せる部分が多い。左右のペインに関するテストは書き直し

案C かんたん編集：準備と編集を分ける

最初に「アバター、直すパーツ、角度」の3つを選ぶ画面を出し、あとは自動で用意します。編集画面にはビュー、キーの切り替え、ツールの3つだけを置きます。それ以外はすべて「詳細」に入れます。

試す：「編集をはじめる」で編集画面に移ります。上の角度を押すとキーが切り替わります。「詳細」で隠れている項目を確かめられます。

性能とリソース

変わること

  • 今の6手順のうち「グループ」「対象Mesh」「キー」の3つが、最初の画面の選択で済む（A2, A6, B5）
  • 編集画面に常に出ている操作は、キー、ツール3つ、保存、元に戻すだけになる（B1, B2）
  • 手順ガイドの行はなくなる。次にやることはステータスの1行に出す（F1, F2）
  • ふだん使わない項目は「詳細」にまとめる（A7, B3, C2）

長所と短所

  • 長所：はじめての人が迷う所がいちばん少ない
  • 長所：編集画面は今の部品の組み替えで作れる。実装は3案でいちばん軽い
  • 短所：キーのあいだの補間や効く範囲は、図では見えないまま（A1 は一部しか解決しない）
  • 短所：角度どうしの見比べは、キーを切り替えて行う
  • 短所：「詳細」に入れた項目は見つけにくくなる。慣れた人には一手間増える
  • 影響：左右のペインがなくなるので、要素名の契約は変わる。プレビューまわりは残る
